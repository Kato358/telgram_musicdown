# v0.1.3 跨挂载点落盘不再 EXDEV

服务器上的表现是「下载明明跑完了，最后一步崩」：大小校验通过、`save_path` 里的歌手目录也建出来了，接着 `[Errno 18] Invalid cross-device link` 把任务打成崩溃，退避三次、音频白下三遍，最后落 `failed`。原因是 compose 把宿主机两份目录**分别**挂成 `/data/data` 与 `/data/downloads`——Linux 的 `rename(2)` 不许跨 mount 改名，哪怕这两个挂载点背后是同一块盘。默认目录布局（`temp=data/temp`、`save=downloads`）在这个布局下天然跨设备，所以本地开发（单一目录树）复现不出来。

- **`app/utils/fs.py` 的 `move_into_place`**：同盘仍是一次原子 rename（行为不变）；跨盘退化成「复制到目标同目录的 `.曲名.xdev.<pid>.<随机>` → `fsync` → 同目录 rename → 删源分片」。中转文件刻意放在**目标同目录**，于是正式路径上要么没有文件、要么就是完整文件，半截 flac 不会进曲库被扫描器/试听读到
- **失败不外溢**：复制中途出错（写满盘、挂载断了）时目标仍是空的，源分片留着给重试；`EACCES` 这类错误**不**触发复制兜底，否则真实原因会被一次注定失败的复制盖住
- **读数不变**：`mtime` 随 `copy2` 一起搬过去，曲库扫描按 `(mtime, size)` 判变更的逻辑不用跟着改
- **部署侧的可选优化**（compose 注释里记了）：`TGM_TEMP_DIRECTORY=/data/downloads/.temp` 把中转区收到曲库同一挂载点，就完全省掉那次整文件复制。曲库扫描跳过头部是点的目录，不会把它当歌；SQLite 与日志固定在 `/data/data`，不受这个开关影响——数据库不该落到 NAS 挂载点上
- **测试**：`tests/unit/test_fs.py`（同盘 / 跨盘 / 缺父目录 / 复制中途失败 / 非跨设备错误外溢 / WinError 17 判定）+ 一条端到端回归：伪造 `temp → 曲库` 跨设备，断言任务 `success`、字节完整、temp 与目标目录都无残骸

升级后旧库里那些 `failed` 直接在下载页点重试即可（重试会先丢掉残留分片重下一遍）；`/data/data/temp/task_*` 是这次事故留下的孤儿分片，可以手工清掉回收空间。

## 镜像

```bash
docker pull ghcr.io/kato358/telgram_musicdown:0.1.3
docker pull ghcr.io/kato358/telgram_musicdown:0.1
```

`:latest` 仍跟着 `main`；`:0.1` 随本条移动到 0.1.3。要锁版本就把 compose 里的 `image:` 钉到 `:0.1.3`。
